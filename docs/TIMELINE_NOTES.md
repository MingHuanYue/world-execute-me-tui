### 1.2 两两对齐偏差（先去掉全局中位偏移，再统计残差）

| 对比 | 一对一匹配 | 全局偏移中位 | 残差中位 | 残差最大 |
|---|---|---|---|---|
| A `lyrics.json` ↔ A `SRT/LRC` | 129 / 129 | 0 ms | **0 ms** | **0 ms** |
| K `lyrics.lrc` ↔ A | 128 / 128 | 0 ms | **0 ms** | **0 ms** |
| B3 `word_timeline` ↔ A | **98 / 98**（B3 全部落在 A 上） | −35 ms | 132 ms | 1081 ms |
| C mode4 ↔ A | 55 / 65 | +107 ms | ~112 ms | 6919 ms |
| C mode5 ↔ A | 75 / 170 | +53 ms | 236 ms | 6812 ms |

解读：

- **A 内部三份文件是同一份数据**（SRT / LRC / JSON 全部 0 ms 一致），所以 A 自身不提供独立验证。
- **K 是真正独立的第二来源**，0 ms 复现 128 条 —— 但它恰好只缺 A 的第 117 行（**t = 178.173 s**），所以 K = 129 − 1。
- **B3 的 98 条全部是 A 的子集，0 条多余**。它的偏移中位只有 −35 ms，说明两个来源用的是同一版 LRC 时间戳；残差中位 132 ms 来自声学强制对齐本身的抖动（该文件自述 `status: AUTOMATIC_DRAFT_REQUIRES_LISTENING_REVIEW`、`method: HDEMUCS vocals; MMS_FA and Whisper medium.en forced alignment; bounded LRC search`，`timing_note: 这些是声学估计，不是人工核对的帧级起音`）。
- **C 只是部分可信的第三来源**。mode4 只覆盖 0–138.25 s，且 65 条里仅 55 条能在 ±0.6 s 内对上 A。我做了随机零模型（把 A 的时间戳打乱后重测）：170 条的 mode5 在 ±0.5 s 内的期望命中是 80.7，实测 129；65 条的 mode4 期望约 31，实测 56。**信号真实存在，但不足以当作逐句字幕轨**——所以 C 只用来给能对上的行加一点置信度，不参与定行数。

## 2. 「131 句」的实测答案：**129**

### 2.1 实测

八个可数对象全部数过：**129 / 129 / 129 / 128 / 102 / 98 / 65 / 170**。

- **没有任何一个来源给出 131。**
- 129 是唯一有三重内部互证的数字（SRT 块 129、lyrics.json 129、LRC 129 个唯一时间戳，0 ms 一致），且被独立仓库 K 复现到 128。
- **B3 的 98 条没有一条是 A 之外的新行**（0 条 unmatched），所以 A 不存在"漏行被别的来源补上"的情况。

### 2.2 差异逐条解释

| 数字 | 与 129 的差 | 原因 |
|---|---|---|
| K = 128 | −1 | K 的 LRC 缺 A 的第 117 行（t=178.173 s）。K 的其余 128 条与 A **0 ms** 完全一致，属同一版 LRC 的少一行副本。 |
| B2 = 102 | −27 | 这是**另一版歌词**（lrclib），且是只存 sha256 的 sidecar，**没有时间戳**，无法逐句比对；它的 id 空间是 0–101。 |
| B3 = 98 | −31 | 同一版 B 歌词里能给出逐词对齐的行。101 个 LRC 槽位中 id 8 / 66 / 99 整行缺失（无词、无行），另有 31 条 A 行没拿到逐词时间。 |
| C4 = 65 | −64 | 弹幕 mode4 只覆盖 0–138.25 s（该区间内 A 有 86 行）。 |
| C5 = 170 | +41 | mode5 混入了非歌词固定弹幕，±0.5 s 命中 129 条、其余 41 条为噪声。 |
| 主人说的 131 | +2 | **在现有数据里复现不出来。** |

### 2.3 那 2 条可能在哪（需要人眼确认，我做不到）

131 − 129 = 2。两种可检验的解释：

1. **非歌词字幕卡**：片头说明/片尾信息这类固定字幕被计入"句数"。
2. **A 把 2 组相邻短句并成了 1 块**：则 A 的 129 块里应有 2 块内部含两句话。

我查了能查的：A 的 129 行**没有异常行**（无 `end ≤ time`，无空文本，时长中位 1.18 s、最大 4.50 s，与邻居无重叠）。所以若真要补 2 条，只可能在**硬字幕里看得见、而 A 未收录**的位置。下面的区段是可判定的候选，建议人眼核对：

- 20.500 → 29.709（9.209 s 空档）
- 135.724 → 147.660（11.936 s 空档）
- 195.856 → 205.811（9.955 s 空档）
- t = 16.000 那一行（**显示但无声学对齐**，见 §3）

我无法 OCR 视频硬字幕，这一条**我没有能力闭环**，如实标为未解决。

## 3. 哪些行置信度低、为什么

置信度模型（可在 `build_timeline.py` 复算）：

```
conf = 0.85                       # 基准: A 的 time/end, 三份同源文件 0ms 互证
     + 0.07  该行有逐词声学对齐(B3)          # 独立声学证据证明这行确实被唱出
     + 0.03  B3 声学起点与 A 时间戳差 ≤150ms  # 两来源高度吻合
     + 0.05  有弹幕(mode4)在 ±0.6s 内命中      # 第三来源支持
上限 0.99
```

| 置信度 | 行数 | 含义 |
|---|---|---|
| 0.99 | 37 | 三来源齐（A + 逐词 + 弹幕 + 紧对齐） |
| 0.97 | 17 | A + 逐词 + 弹幕 |
| 0.95 | 18 | A + 逐词 + 紧对齐 |
| 0.92 | 26 | A + 逐词 |
| 0.90 | 1 | A + 弹幕（无逐词） |
| **0.85** | **30** | **仅 A；无声学对齐、无弹幕支持** |

**低置信行 = 31 条（`confidence ≤ 0.90`），且它们与"无逐词行"完全同一批**，时间点：

```
2.920  6.380  13.891 16.000 32.682 36.287 40.049 43.507 59.687 63.535
69.259 73.169 76.959 80.620 84.268 87.922 104.197 110.900 117.274 118.979
122.714 158.900 160.244 161.124 163.315 168.911 172.712 178.173 183.646 187.665 191.356
```

原因分类：

1. **落在器乐/间奏段**：158.9 / 160.244 / 161.124 / 163.315 / 168.911 / 172.712 共 6 条落在阶段 1 判定的 `instrumental_execution` 段（142.00–161.91）及其后的 `outro_develop` 开头。**这是一条值得回传的观察：那一段并非"纯器乐"——A 在该段仍有 21 行字幕，只是全都没有逐词对齐。**
2. **落在句间长空档的边缘**：16.000（大空档起点）、43.507 / 73.169 / 110.900 / 117.274 / 118.979（章节过渡帧区域）。
3. **B3 对齐失败**：如 178.173（正好是 K 缺的那一行）。B3 是自动草稿，缺对齐不等于没唱。

这些行的**时间戳本身仍来自 A（与其他行同等精度）**，低置信指的是"缺少独立来源佐证"，不是"时间不可靠"。渲染层若要保守，可把 `confidence < 0.9` 的行按普通行处理即可。

## 6. 逐词数据

- 395 词全部来自 B3（`skeleton.words`，每词带 `index` → 输出为 `wid`）。
- 一行有逐词 → 输出该行全部词；**没有对齐的行输出 `words: []`，不编造**（31 行）。
- 每行词数中位 4（1–8）。
- 对齐处理：若 B3 行起点与 A 行起点相差 ≤0.5 s，则把该行所有词平移 `Δ = A.t − B3.start`，使词锚定在 A 的时间基上（B3 与 A 的全局偏移中位仅 −35 ms，所以平移量很小）；词尾统一截到 206.994 s。

- 对**解码后的 JSON**（裸文件里中文是 \uXXXX 转义，会藏住文本）做整行子串检索：命中 54 条，**全部是同一个 9 字符字符串 `EXECUTION`** —— 它既是 lead 指定的章节 07 名称，又恰好与部分歌词行同形。`timeline.json` 里它**只出现 1 次**，就是 `chapters[6].name`（已实测计数）。

## 9. 仓库路径占位符（与红线有关）

`meta.sources[].path` 里写的是 `<repo_A>` / `<repo_B>` / `<repo_K>` **占位符，不是真实目录名**。

原因：这三个仓库的目录名里含**歌曲标题**词形，而标题恰好也是某句歌词（18 字符）的前 13 个字符。为把"产物里不出现歌词文本"做到可机检的严格程度，产物与构建脚本里都不写真实目录名 —— `build_timeline.py` 改为**按特征文件动态发现仓库**（含 `lyrics.json` 的 / 含 `data/timing/word_timeline_notext.json` 的 / 含 `assets/lyrics/lyrics.lrc` 的），匹配唯一。

映射：`repo_A` = `_ref/repos/` 下含 `lyrics.json` 的仓库；`repo_B` = 含 `data/timing/word_timeline_notext.json` 的仓库；`repo_K` = 含 `assets/lyrics/lyrics.lrc` 的仓库。

## 10. 泄漏检查的最终指标：最长公共子串

子串/整行匹配会被通用词干扰，所以最后用**最长公共子串**作决定性判定：把每个交付文件与 1009 条候选文本（A 的 en/zh、LRC 全文行、弹幕全文）逐条求最长公共子串。

| 文件 | 最长公共子串 | 该片段是什么 | ≥12 字符 | ≥20 字符 |
|---|---|---|---|---|
| `data/timeline.json` | **9 字符** | 章节名 `EXECUTION` | 0 | 0 |
| `docs/TIMELINE_NOTES.md` | **11 字符** | 同上（章节表格里的 `EXECUTION 148.0–175.3`） | 0 | 0 |
| `data/build_timeline.py` | **10 字符** | 章节名片段（`REWARD_HACK`） | 0 | 0 |

即：**除 lead 指定的章节名 `EXECUTION` 外，三个文件与全部歌词/弹幕文本的最长公共子串不超过 11 个字符；没有任何一句歌词的 12 个连续字符出现在任何产物里。** `timeline.json` 原始字节的非 ASCII 字符数为 **0**。
