# FX_BUDGET.md — 宏大场面的 Pillow 开销预算（实测）

> 执行者：qa-integrator（task-7）
> 目的：为 DESIGN.md《宏大场面设计》提供**实测**性能预算，回答「粒子走哪条路 / 5 级宏大帧掉到多少 fps / 4K 撑不撑得住」
> 方法：全部 Pillow + ImageDraw，`time.perf_counter()` 真实墙钟，**每项 30 帧取中位数**（预热 3 帧丢弃），随机数统一 `random.Random(0)`
> 脚本：`_ref/fxbench/`（fxbench.py / fxbench_e2e.py / fxbench_e2e2.py / fxbench_extras.py / fxbench_opt.py / fxbench_break.py；原始 JSON 同目录）
> 分辨率：720p = 1280x720，4K = 3840x2160
> 编排：每个「单帧」测量都包含 `base.copy()`（因为每帧都要从干净画布重绘），另单列「边际成本」= 总耗时 − base.copy()

---

## 0. 三句话结论

1. **粒子路线：A（point 直画）最快，C（预渲染 sprite + paste）次之，B（RGBA 椭圆 + alpha_composite）最慢且 4K 下不可用。**
   边际成本 720p：A **0.10 ms** vs C 4.90 ms vs B 4.99 ms（A 快 **约 50 倍**）；
   4K：A **2.97 ms** vs C 4.84 ms vs B **33.44 ms**（B 是 A 的 **11 倍**）。
2. **5 级宏大帧把 147.6 fps 打到 ~39 fps（裸实现）；但做三处优化后只掉到 ~97.5 fps。**
   优化点：① 全屏 alpha_composite → `Image.blend`；② token 雨改预渲染 sprite；③ 星系拓扑预计算。
   720p 单帧：裸 **25.0 ms / 39.9 fps** → 优化 **10.26 ms / 97.5 fps**（**快 2.4 倍**）。
3. **4K 可行**（优化后 12.1 fps，全片 5085 帧 ≈ 7.0 min，60s 高潮 ≈ 2.0 min）。
   **但任务里建议的「粒子数按面积反比缩」实测只省 1.9 ms（4%）——不是有效手段。**
   4K 真正的瓶颈是**全屏内存带宽操作**（base.copy + 全屏上色 ≈ 41 ms / 46 ms = **89%**），杠杆在别处。

| 8) 结构解体 24×14 tile | 31.15 | 32.1 | 21.08 | |
| 9) **5 级宏大帧（裸实现）** | **118.93** | **8.4** | — | |
| 10) 5 级 + 碎裂（裸实现） | 136.47 | 7.3 | — | |

### 2.1 全屏上色的四种做法（4K，含各自动作）

| 做法 | ms | 相对 alpha_composite |
|---|---|---|
| `Image.alpha_composite`（整幅 RGBA 层 + 2 次 convert） | 71.05 – 73.94 | 1.00× |
| `Image.blend(img, 预建纯色, a/255)` | **31.14** | **2.29× 更快** |
| `ImageChops.multiply` | 37.5 – 38.5 | 1.9× 更快 |
| `ImageChops.lighter` | 26.8 – 27.6 | 2.6× 更快 |

★ **`Image.blend(img, 纯色, a/255)` 与「alpha 合成一层纯色」数学等价**
（`out = C·a + img·(1−a)`，这正是 alpha_composite 对不透明底的结果），
所以**全屏纯色染色应一律用 blend**，不要用 alpha_composite。只有需要**逐像素变化的 alpha**（渐变/vignette/按区域擦除）时才用 RGBA 合成。

## 3. 「5 级宏大场面帧」总账

定义（按任务清单）：粒子 2000 + 透视网格 80×40 + 星系 120 节点（235 条去重边）+ token 雨 300 + 全屏 alpha 层（+ 可选碎裂）。

| 配方 | 720p 渲染 ms | 720p e2e ms | 720p e2e fps | 4K 渲染 ms | 4K e2e ms | 4K e2e fps |
|---|---|---|---|---|---|---|
| **裸实现**（draw_text + alpha_composite + 逐帧 kNN） | 21.50 – 27.44 | **25.02** | **39.9** | 111.0 – 118.9 | **~148** | **~6.8** |
| **裸实现 + 碎裂** | 31.24 | 29.02 | 34.5 | 136.5 | 未直接测（渲染 136.5 + 编码 ~37 ≈ 173 折算） | ~5.8（折算） |
| **优化实现**（见 §4） | **6.58** | **10.26** | **97.5** | **47.94** | ~85（折算；实测的面积反比缩配方为 82.64） | ~11.8（折算） |
| **优化实现 + 碎裂** | 9.41 | 14.48 | 69.1 | 66.79 | ~104（折算） | ~9.6（折算） |
| 优化 + 面积反比缩到 4K（222/44×22/40/150） | — | — | — | 46.02 | **82.64** | **12.1** |

e2e = 渲染 → rawvideo 管道 → libx264 `-preset veryfast -crf 18`。
**编码开销实测**：720p ≈ **3.4 ms/帧**，4K ≈ **37 ms/帧**（由「渲染 111.0 → e2e 148」与「渲染 46.0 → e2e 82.6」两次反推，互相一致）。
表里未直接实测的 e2e 已标注「折算」。

### 3.1 与 ENV_REPORT 基线的对比

| 口径 | 数值 |
|---|---|
| ENV_REPORT 基线：普通帧端到端 | **6.78 ms = 147.6 fps**（渲染+管道+x264，当时渲染器较轻） |
| 本基准 base 帧渲染（720p） | 7.20 ms = 138.9 fps（3 面板 + 30 行文字，本基准的「普通帧」） |
| **5 级宏大帧（裸实现）** | **25.0 ms = 39.9 fps → 掉到基线的 27%**（慢 3.7×） |
| **5 级宏大帧（优化）** | **10.26 ms = 97.5 fps → 保留基线的 66%**（慢 1.5×） |
| 5 级 + 碎裂（优化） | 14.48 ms = 69.1 fps → 基线的 47% |

**回答主问题：一个 5 级宏大帧会把 147.6 fps 打到 ~39 fps（裸实现）或 ~97.5 fps（优化后）。**

### 3.2 ETA

| 场景 | 裸实现 | 优化实现 |
|---|---|---|
| 720p 纯渲染 5085 帧 | 21.5 ms × 5085 = **109 s** | 6.58 ms × 5085 = **33.5 s** |
| 720p 端到端 5085 帧 | 25.0 ms × 5085 = **127 s ≈ 2.1 min** | 10.26 ms × 5085 = **52 s** |
| **720p 仅高潮段 60 s = 1440 帧** | **36.0 s** | **14.8 s** |
| 720p 高潮段 + 碎裂 1440 帧 | 41.8 s | 20.9 s |
| 4K 纯渲染 5085 帧 | 111 ms × 5085 = **9.4 min** | 47.9 ms × 5085 = **4.1 min** |
| 4K 端到端 5085 帧 | 148 ms × 5085 = **12.5 min** | 82.6 ms × 5085 = **7.0 min**（实测配方） |
| **4K 仅高潮段 60 s = 1440 帧** | **3.6 min** | **2.0 min** |
| 4K 高潮段 + 碎裂 1440 帧 | 173 ms × 1440 = **4.2 min**（折算） | 104 ms × 1440 = **2.5 min**（折算） |

> 全片 5085 帧数来自 `_ref/sections.json`/ffprobe（211.874938 s × 24 = 5085 帧，见 REFERENCE_VERIFICATION.md §9）。
> 注意：宏大帧只出现在高潮段，不是全片 5085 帧都跑满；上表「5085 帧」是**假如全片都宏大**的悲观上界。

## 4. 三处优化的实测收益（720p / 4K，渲染单帧）

| 优化 | 做法 | 720p 收益 | 4K 收益 |
|---|---|---|---|
| ① 全屏染色：alpha_composite → `Image.blend`（纯色预建，勿每帧新建） | 数学等价 | 7.42 → 3.43 ms（省 4.0 ms） | 71.05 → **31.14 ms**（省 **40 ms**）★ |
| ② token 雨：`draw_text` → 预渲染字形 sprite + paste | 每种 token 只栅格化一次 | 13.65 → **2.28 ms**（**5.9×**） | 36.23 → **16.04 ms**（2.3×） |
| ③ 星系拓扑：逐帧暴力 kNN → 预计算（或每 N 帧重算） | kNN 与分辨率无关，纯 Python 4.9 ms/帧 | 4.92 → ~0 ms（省 4.9 ms） | 4.85 → ~0 ms（省 4.9 ms） |

三项合计：720p 27.44 → 6.58 ms（**3.4×** 提速）；4K 118.93 → 47.94 ms（**2.5×** 提速）。

**② 的适用前提**：token 文本集合有限（本片歌词 token 全集可一次预渲染）。若每帧文本都不同则无效——但本片不是。
**③ 的做法**：节点位置可动、拓扑每 0.5 s（12 帧）重算一次即可，摊薄到 0.4 ms/帧。

## 5. 4K 可行性判定与降级策略

### 5.1 判定：**可行**

- 优化后 4K 宏大帧 **12.1 fps**；即便全片 5085 帧都按宏大帧渲染也只需 **7.0 min**；60 s 高潮段 **2.0 min**。
- 裸实现 6.8 fps 也并非不可接受（全片 12.5 min，高潮 3.6 min）——**4K 不会被性能否掉**。

### 5.2 ⚠ 任务建议的「粒子数按面积反比缩」实测无效

| 4K 配方 | 渲染 ms | 相对全密度 |
|---|---|---|
| 优化 + **全密度**（2000 粒子 / 80×40 / 120 节点 / 300 token） | 47.94 | 1.00× |
| 优化 + **面积反比缩**（222 粒子 / 44×22 / 40 节点 / 150 token） | 46.02 | **仅快 4%** |

**原因**：4K 下一帧 46 ms 里，`base.copy()` 10.2 ms + 全屏染色 31.1 ms = **41.3 ms（89%）**，
而粒子+网格+连线+token 加起来只有约 5 ms（Pillow 的 point/paste 是 C 循环，2000 个点只要 ~0.7 ms）。
→ **减少粒子数省不到东西。**

### 5.3 正确的 4K 降级策略（按实测收益排序）

1. **【省 40 ms】** 全屏纯色染色一律用 `Image.blend`，禁止对整幅做 `alpha_composite`。
   只有渐变/vignette 这类逐像素 alpha 才付出 RGBA 合成的代价，且尽量把这类镜头限制在少数帧。
2. **【省 10 ms】** 消除多余的整帧拷贝。本基准每帧都要 `base.copy()`（10 ms）；
   若渲染器能**直接在自己的画布上画 FX**（而不是拷一份再叠加），这一项为零。
   需要「FX 不污染 UI 层」时，优先用预先算好的 mask 局部贴，而不是整帧复制。
3. **【省 ~16 ms】** token 雨与粒子用**预渲染 sprite + paste**（§4②）。
4. **【省 21 ms，仅碎裂镜头】** 结构解体的 tile 数从 24×14 降到 12×7（336→84 块），或只在解体的关键 1–2 s 用满 336 块。
5. **【省 4.9 ms】** 星系拓扑预计算（§4③）。
6. **【不推荐】** 单纯砍粒子数——4K 下只省 4%。

### 5.4 如果一定要「4K 全片都宏大」

优化后 4K 全片 ≈ 7.0 min（端到端）。这个预算内**不必**降级；只有在需要 < 3 min 时才需要动 §5.3 的 4–5 项，
或者采用「720p 渲染 + 3× nearest-neighbour 放大」——但那正是原片做法（见 REFERENCE_VERIFICATION.md §9），
终端文字会发虚，不建议。

## 6. 三条实现细节（会影响设计能不能按预期实现）

### 6.1 ⚠ 半透明椭圆**不会叠加发光**，只互相覆盖

```
RGBA 层上画一个 (255,0,0,128) 椭圆，重叠再画一个同色：重叠像素 alpha 仍为 128（REPLACES）
ImageDraw.Draw(im, "RGBA") 模式同样如此（实测）。
```

→ 想靠「多层半透明椭圆堆叠」做出粒子核心亮斑**行不通**。
正确做法：① 粒子画**不透明**核（1px point，路线 A）；② 需要柔光时用**预渲染好的 sprite**（路线 C，sprite 内部已含渐变）；
③ 需要叠加发光时用 `ImageChops.add/lighter` 或对 mask 取 `ImageChops.lighter` 后再上色。

### 6.2 粒子路线的取舍

| 需求 | 用哪条 | 理由 |
|---|---|---|
| 星点 / 1px 粒子 / 3000 以下 | **A（point）** | 720p 边际 0.10 ms，4K 2.97 ms |
| 需要 2px+ 柔光、有辉光边缘 | **C（sprite paste）** | 720p 4.90 ms，4K 4.84 ms |
| 需要逐粒子随机大小/颜色 | **C**（多准备几种 sprite） | 预渲染 4–8 种即可 |
| ❌ 不要用 | **B（RGBA 椭圆 + alpha_composite）** | 4K 边际 33.4 ms，且 §6.1 的覆盖问题 |

### 6.3 分辨率无关的部分 vs 面积相关的部分

| 只在 CPU / 与分辨率无关 | 随像素面积线性增长 |
|---|---|
| 星系 kNN 拓扑计算（4.9 ms，两个分辨率相同） | `base.copy()`、全屏 blend / composite、tile 粘贴、draw_text/sprite 的像素填充 |
| 坐标计算、事件表、随机数 | |

→ 设计上应把「每帧要做的数学」压到常数级，把「每帧要碰的像素」压到最少。
本基准里 4K 89% 的时间都花在碰像素上。

## 8. 不确定项

1. **4K 优化 e2e 的 82.64 ms 是「面积反比缩」配方**；全密度配方的 e2e 未直接实测（按渲染 47.94 + 编码 ≈ 35 ms 折算为 ~83 ms，标注为折算值）。
2. **1/3 处数值有 ±5–15% 的跑动**（同配置两次测量差异，如 720p 裸实现 21.50 vs 27.44 ms，差异来自第一次是否含逐帧 kNN）。
   已尽量在表中并列区间；写进 DESIGN.md 时建议取**优化后**的稳定值。
3. **未测内存峰值**。4K 全屏 RGBA 方案会同时持有 RGB + RGBA + 层 = 约 100 MB，本机 15.85 GB 可用，不构成风险，但未实测。
4. **未测多线程**。Pillow 的 point/paste 部分释放 GIL；用 `concurrent.futures` 按行分块可能进一步提速，**本轮未验证**。
5. **碎裂的视觉质量未评估**（只测了开销）：336 块 tile 的偏移量与视觉「解体感」的关系需要美术判断。
